### A Collabrative Partnership with Customers
#### User classes
- We may have **distinct groups** of user for a product
- We can divide them from following aspects:
	- Frequency of use of product
	- Functions used
	- Tasks to be accomplished
	- education and skill level
	- previlege or security level
- Identify user classes and their charaterisitics early and **document** them in SRS
- But, **not all of them** are important or saying equally important

> Learn more from 
> *Gause and Lawrence, "User-Driven Design", Software Testing & Quality Engineering Jan/Feb 1999*

- User class is not enough, we need **product champion**
	- Product Champion can represent the need of this user class

### Understanding User Requirements
#### Use Case approach
- **Definition**: a description of a set of **interaction sequences** that a system performs to provide a result of observable or **measurable value** to one or more **actors**
- We describe:
	- user goals
	- the user's view of the system
	- a set of task-related activities

#### The Use Cases and Functional Requirements
- There are 2 schools of thought:
	- Use Cases ==are== Functional Requirements
	- Use Cases ==reveal== Functional Requirements

### Other things
#### How to name use cases
- **"FORM"**: ***active verb + object***
- Good Example:
	- Reseve Rental Car
	- Print Invoice
	- Check Flight Status
- Not So Good Example:
	- Enter Pin
	- Submit Form 37
	- Process Deposit
